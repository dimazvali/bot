# QR AR-окна в прошлое — Design Spec

**Date:** 2026-08-25
**Project:** AR-таблички на исторических местах Тбилиси — наведя камеру на QR-код, видишь старое фото этого же места как «окно», с параллаксом при повороте телефона
**Domain:** qr.dimazvali.com
**Stack:** Node.js + Express + Pug (по паттерну существующих сабпроектов, например `pelamushi`/`photo`), без сборщика на клиенте — vanilla JS + CSS

---

## 1. Контекст и миссия

Физические таблички с QR-кодом развешиваются на местах в Тбилиси, где сохранились исторические фотографии этого же места (площадь, улица, здание). QR-код ведёт на страницу `qr.dimazvali.com/<slug>`, которая же самим кодом используется как AR-мишень: наведя камеру, пользователь видит старое фото, «вмонтированное» в текущий вид через камеру, как окно в прошлое. Поворачивая телефон, можно заглянуть за края окна — фото сдвигается иначе, чем рамка портала, создавая ощущение глубины.

Один физический QR = одна страница = одна историческая фотография.

---

## 2. Архитектура

### Подключение к существующему Express-приложению

```js
// app.js
app.use(vhost('qr.dimazvali.com', require('./routes/qr')))
app.use(vhost('qr.*.*', require('./routes/qr')))
app.use(vhost('qr.localhost', require('./routes/qr')))
```

### Структура файлов

```
routes/
  qr.js              — публичная страница + монтирование admin-роутера
  qr-admin.js         — админка (список, добавить/редактировать, скачать QR PNG)

lib/
  qr-data.js          — чтение/запись data/qr-photos.json, работа с файлами картинок

views/qr/
  layout.pug
  photo.pug            — единственная публичная страница (карточка + AR-сцена)
  admin/
    layout.pug
    list.pug
    edit.pug

public/javascripts/qr/
  ar.js                — вся клиентская AR-логика (сканирование QR, анкер, параллакс)
  jsQR.js               — вендоренная копия jsQR (UMD, без npm-зависимости на клиенте)

public/qr/<slug>/
  photo.jpg             — загруженное историческое фото

data/
  qr-photos.json        — массив записей (см. ниже)
```

Всё по существующему паттерну проекта: отдельный vhost-роутер на сабдомен, JSON-файл как хранилище (как `data/photo.json`), Pug-вьюхи, никакого фронтенд-сборщика — клиентский JS лежит в `public/` и подключается тегом `script`.

## 3. Данные

`data/qr-photos.json` — массив объектов:

```js
{
  slug: "erekle-square",        // уникальный, часть URL
  title: "Площадь Ираклия II",
  year: "1930-е",
  description: "Краткое описание места/фото",
  address: "необязательно, для подписи на странице",
  photo: "/qr/erekle-square/photo.jpg",
  createdAt: 1735000000000,
  updatedAt: 1735000000000
}
```

Фото должно быть заметно крупнее области портала (по замыслу — иначе нечего «открывать» по краям при повороте); это учитывается в UI загрузки в админке подсказкой, но жёсткого ограничения по размеру нет.

`lib/qr-data.js` — простой файловый CRUD (read/write JSON + сохранение загруженного файла в `public/qr/<slug>/photo.jpg` через `sharp`, ресайз/компрессия как в `photo-data`/`photo-admin`).

## 4. Роуты

### Публичный (`routes/qr.js`)

| Маршрут | Действие |
|---|---|
| `GET /:slug` | Страница с фото + AR-сценой. 404 если slug не найден |

### Админка (`routes/qr-admin.js`, монтируется на `/admin` внутри `qr.js`)

Защита — cookie-пароль по образцу `photo-admin` (`signed cookie`, `papersToken`-based HMAC).

| Маршрут | Действие |
|---|---|
| `GET /admin` | Логин (если не авторизован) или список записей |
| `POST /admin/login` | Проверка пароля, установка cookie |
| `GET /admin/new` | Форма создания |
| `POST /admin/new` | Создание записи (multipart: фото + поля) |
| `GET /admin/:slug/edit` | Форма редактирования |
| `POST /admin/:slug/edit` | Обновление записи (фото опционально) |
| `POST /admin/:slug/delete` | Удаление записи и файла |
| `GET /admin/:slug/qr.png` | PNG QR-кода на `https://qr.dimazvali.com/<slug>` (через пакет `qrcode`, уже есть в зависимостях) — для скачивания и печати таблички |

## 5. Публичная страница и AR-сцена

### Состояния экрана (`views/qr/photo.pug` + `public/javascripts/qr/ar.js`)

1. **До AR** — заголовок, год, описание, миниатюра фото, кнопка «Смотреть в AR». Камера/датчики запрашиваются только по клику (обязателен user-gesture, особенно для `DeviceOrientationEvent.requestPermission()` на iOS).
2. **Проверка поддержки** — если браузер не даёт `getUserMedia` или это десктоп без камеры, кнопка «Смотреть в AR» не показывается — просто крупная картинка на странице, без ошибок и лишних сообщений.
3. **Поиск QR** — камера на весь экран (`<video>` + скрытый `<canvas>` для кадров), поверх — подсказка «наведите камеру на QR-код на табличке». Каждый кадр (с троттлингом, не чаще ~10 fps) прогоняется через `jsQR`.
4. **Анкер** — как только QR найден:
   - берём 4 угловые точки QR в системе координат видео;
   - запоминаем текущую ориентацию телефона (`alpha/beta/gamma` из `deviceorientation`) как `O0`;
   - вычисляем начальный экранный quad портала на основе точек QR (с небольшим увеличением — сам портал крупнее QR-метки).
5. **AR-режим** — камера продолжает идти фоном:
   - портал (рамка) — `div` с `transform: matrix3d(...)`, посчитанным как перспективный corner-pin quad, обновляется на каждый `deviceorientation` с компенсацией дельты от `O0` (~1:1), чтобы визуально «держаться» на месте таблички;
   - фото внутри портала — тот же quad, но с бОльшим коэффициентом чувствительности к дельте ориентации (например ×2.5–3, подбирается на глаз) — из-за этого при повороте телефона фото «плывёт» иначе, чем рамка, и его края выходят за портал / скрываются под ним;
   - обрезка — фото зажато `overflow: hidden` контейнером портала, так что видна только его часть — то, что «за углом», просто не видно, пока поворот не подвинет фото в кадр портала;
   - кнопка «навести заново» — сбрасывает состояние в (3), если пользователь увёл телефон и картинка выглядит разъехавшейся.

### Математика портала (кратко, деталь для реализации)

- QR даёт 4 точки → эти точки трактуются как исходный quad, из которого через `DOMMatrix`/ручной расчёт гомографии строится `matrix3d` для CSS-элемента (техника «CSS corner-pinning», без WebGL/Three.js — укладывается в отсутствие сборщика на клиенте).
- Ориентационная компенсация — упрощённая (не полноценный sensor fusion): дельты `alpha`/`beta`/`gamma` от `O0` конвертируются в дополнительный поворот/сдвиг quad'а. Не претендует на идеальную физическую точность — цель ощущение, а не инженерная точность 6DOF-трекинга.

## 6. Ошибки и граничные случаи

- Нет доступа к камере / отказ в разрешении → показываем то же самое, что для неподдерживаемого браузера (пункт 2) плюс текст с объяснением и кнопкой повторить запрос.
- QR не находится долго (например, табличка выцвела/плохое освещение) → через ~15 сек показываем подсказку «попробуйте поднести ближе / больше света», сканирование продолжается.
- iOS требует отдельного разрешения на датчики ориентации (`DeviceOrientationEvent.requestPermission`) — запрашивается тем же кликом «Смотреть в AR» вместе с камерой.
- Если `deviceorientation` недоступен вовсе (часть Android-браузеров/десктоп) — портал и фото просто не двигаются после анкера (статичное окно, без параллакса) — деградация, а не ошибка.

---

## 7. Вне скоупа (сознательно не делаем)

- Непрерывный image-tracking (MindAR/AR.js, продолжающееся распознавание QR как маркера) — отклонено в пользу гибрида «анкер один раз + гироскоп».
- Ручная подготовка нескольких слоёв (foreground/background) для каждого фото — не нужно, эффект глубины даёт разница коэффициентов чувствительности портала и фото, а не отдельные вырезанные слои.
- Мультиязычность, карта/список всех точек, категории/теги — не запрошено, можно добавить отдельным проектом позже если понадобится.
